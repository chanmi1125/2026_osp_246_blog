## 배경 (Context)

이화픽에서 저는 **리뷰 작성** 기능을 맡았습니다. 학생이 제목, 별점, 본문, 사진을 올리면 Firebase Realtime Database에 저장되는 기능입니다.

회원은 이미 `user/<아이디>`, 상품은 `item/<상품 이름>` 경로에 저장되고 있었습니다. 그런데 리뷰는 무엇을 키로 써야 할까요? 한 상품에 리뷰가 여러 개 달리고, 한 학생이 같은 상품에 두 번 쓸 수도 있어서 상품 이름도 아이디도 리뷰 하나를 구별하지 못합니다.

## 다룰 개념 (Goal)

Realtime Database가 데이터를 **키**로 찾는 방식과, 키를 만드는 두 방법인 `set()`과 `push()`의 차이를 설명합니다.

## 개념 이해하기 (Steps)

### 1. 데이터베이스 전체가 하나의 JSON 트리

Realtime Database에는 표나 행이 없습니다. 전체가 **하나의 큰 JSON 객체**이고, 모든 값은 루트에서 시작하는 **경로**로 찾습니다. 이화픽 데이터를 간단히 그리면 이렇습니다.

```json
{
  "user":   { "jiwoo01": { "nickname": "지우", "user_type": "student" } },
  "item":   { "크림빵": { "price": 3000, "seller_id": "bakery_kim" } },
  "review": { "-P6b6Ok0s5A8SmrdfDey": { "product_name": "크림빵", "rating": 5 } }
}
```

`user`, `item`, `review` 아래의 이름표 하나하나가 키입니다. `user/jiwoo01/nickname`처럼 키를 이어 붙이면 값 하나를 가리키는 경로가 됩니다. 그래서 **키를 정하는 일이 곧 데이터를 찾는 방법을 정하는 일**입니다.

### 2. set(): 내가 정한 키에 쓴다

```python
# database.py — 상품 등록 (필드 일부 생략)
def insert_item(self, name, data, img_paths):
    item_info = {"seller_id": data["seller_id"], "price": int(data["price"].replace(",", "")), ...}
    self.db.child("item").child(name).set(item_info)
```

`child("item").child(name)`으로 `item/<상품 이름>` 경로를 만들고 `set()`으로 그 자리에 값을 넣습니다. 키를 알고 있으니 `child("item").child(name).get()` 한 번으로 바로 꺼낼 수 있습니다.

단, **같은 경로에 다시 `set()`하면 이전 값이 통째로 바뀝니다.** "아이디 하나에 회원 한 명"인 데이터에는 이 성질이 맞습니다. 하지만 리뷰를 상품 이름 키로 저장하면 문제가 됩니다.

```python
# 잘못된 예: 리뷰를 상품 이름 키로 저장
self.db.child("review").child("크림빵").set(review_a)
self.db.child("review").child("크림빵").set(review_b)   # review_a가 사라짐
```

두 번째 `set()`이 첫 번째 리뷰를 덮어써서 리뷰가 항상 하나만 남습니다. 계속 쌓여야 하는 데이터에는 겹치지 않는 새 키가 필요합니다.

### 3. push(): Firebase가 키를 만들어 준다

```python
# database.py — 리뷰 저장
def insert_review(self, review_info):
    return self.db.child("review").push(review_info)["name"]
```

`push()`는 `review` 아래에 `-P6b6Ok0s5A8SmrdfDey` 같은 20글자 고유 키를 새로 만들어 저장합니다. 이 키는 만든 시각을 바탕으로 만들어져서 시간순으로 정렬되고, 두 사람이 동시에 써도 겹치지 않습니다. Pyrebase4는 `{"name": "<새 키>"}`를 돌려주므로 `["name"]`으로 새 키를 받습니다.

```python
# app.py — 리뷰 작성 POST (일부)
DB.insert_review({"writer": writer, "product_name": product_name,
                  "title": title, "rating": int(rating), ...})
```

어떤 상품의 리뷰인지는 키가 아니라 **값 안의 `product_name`** 에 적습니다. 키는 리뷰를 구별하는 일만 하고, 상품과의 관계는 필드가 맡습니다. 상품 상세의 평균 별점도 `product_name`이 같은 리뷰만 모아 계산합니다.

### 4. push 키를 주소로 쓰기

`review` 노드를 읽으면 `{push 키: 리뷰}` 딕셔너리가 옵니다. 목록에서는 이 키로 상세 페이지 링크를 만듭니다.

{% raw %}
```html
<!-- review_list.html -->
<a href="{{ url_for('review_detail', review_id=review.id) }}">{{ review.title }}</a>
```
{% endraw %}

링크는 `/reviews/-P6b6Ok0s5A8SmrdfDey`가 되고, 상세 페이지는 `child("review").child(review_id).get()`으로 그 리뷰만 읽습니다.

| 메서드 | 키를 정하는 쪽 | 같은 키에 다시 쓰면 | 이화픽 |
|---|---|---|---|
| `set()` | 개발자 | 덮어씀 | `user`, `item`, `like` |
| `push()` | Firebase | 항상 새 키 | `review` |

## 배운 점 (What I learned)

- **표가 없는 데이터베이스에서는 키 설계가 곧 데이터 설계입니다.**
- **하나만 있어야 하면 `set()`, 쌓여야 하면 `push()`.** 회원·좋아요는 덮어쓰는 성질이 장점이고, 리뷰는 덮어쓰면 데이터가 사라집니다.
- **관계는 필드로 표현할 수 있습니다.** `product_name`을 값에 두니 키는 고유하게, 관계는 따로 관리할 수 있었습니다.
